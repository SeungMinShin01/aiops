# AIOps v0.1 아키텍처 (기준 문서)

- 문서 버전: 1.3 (2026-10-28, MVP 단계 담당제)
- 범위: v0.1 에러 수집 MVP
- 용도: **모든 작업 전에 이 문서와 비교해서 설계가 깨지는지 먼저 확인한다.** 바꿀 때는 아래 "결정 기록"과 "변경 이력"을 함께 고친다.

---

## 0. 한 문장

팀 앱에 의존성 한 줄을 넣으면, 로컬에서 난 런타임 에러가 가려진 채로 서버에 모이고, 같은 에러끼리 묶여, 새 에러에는 AI 설명이 붙어 디스코드로 오며, Grafana에서 확인된다.

**범위 안:** 에러 수집, 마스킹, 전송, 저장, 그룹핑, AI 설명, 디스코드 알림, Grafana, 배포
**범위 밖 (이후 버전):** RLS 멀티테넌시(v0.2), 웹 콘솔(v0.3), 성능 분석(v0.4), Redis 큐(v0.5)

## 1. 레포 구조 (모노레포, Gradle 멀티 모듈)

```
aiops/
├ settings.gradle / build.gradle / gradle.properties
├ protocol/      ⓟ Starter와 서버가 함께 쓰는 데이터 형식 (순수 Java)
├ starter/       ①~⑪ 팀 앱에 들어가는 라이브러리
├ server/        ⑫~⑰ 수집 서버 + 처리기
├ sample-app/    일부러 에러를 내는 테스트용 앱
├ infra/         local(docker-compose), vm(배포용 compose, Caddy), grafana
├ docs/          이 문서, 결정 기록
├ .github/       CI 워크플로우, PR 템플릿
└ jitpack.yml    protocol + starter만 라이브러리로 배포
```

## 2. 전체 흐름

```
[팀 앱 안: Starter]
 ① 설정 → ② 초기 연결기 → (부품 생성·장착)
 에러 발생 → ③ Appender → ④ Mapper → ⑤ Masker → ⑥ Buffer ═ 경계 ═ ⑦ Sender → ⑧ Transport ──┐
 ⑨ 시작 실패 처리기 / ⑩ 종료 처리기 / ⑪ 환경 수집기                                       │
                                                                                         ▼ HTTPS
[우리 서버]
 ⑫ 키 인증 → ⑬ 수집 API → (저장, 202) → ⑭ 그룹핑 → ⑮ AI 설명 → ⑯ 알림
 ⑰ 보존 기간 삭제
[공통] ⓟ protocol 모듈
```

**스레드 경계:** ⑥ `offer()`까지는 팀 앱 스레드(대개 Tomcat 요청 스레드), 그 이후는 Starter 전용 데몬 스레드(aiops-sender).

## 3. 부품별 명세

형식: 역할 / 언제·누가 실행 / 입력 → 출력 / 꼭 지킬 것 / 실패하면

### ⓟ protocol 모듈
- 역할: 주고받는 데이터 형식을 한 곳에 정의 (`EventBatch`, `AppInfo`, `ErrorEvent`, `ErrorCause`, `StackFrame`, `Phase`, `HelloRequest`, `Dependency`, `ConfigKey`, `ConfigSource`, `ProtocolConstants`)
- 꼭 지킬 것: Spring 의존 없는 순수 Java. 필드 **추가만** 허용, 삭제·이름 변경 금지. `ConfigKey`에는 **값 필드가 없다**
- 실패하면: 한쪽만 바꾸면 컴파일 에러로 드러남

### Starter

| # | 부품 | 역할 | 실행 스레드 | 꼭 지킬 것 | 실패하면 |
|---|---|---|---|---|---|
| ① | AiopsSettings | `aiops.*` 설정 읽기 | main | 수집 주소는 기본값 내장 | 키 없으면 경고 한 줄 + Starter 전체 비활성 |
| ② | AiopsEarlyInitializer / AiopsRuntime | 부품 생성, Appender 장착, sender 시작, 종료 훅 등록 | main | `spring.factories` 리스너, **Spring 로깅 초기화 직후** 실행. 부품은 JVM당 1회 생성, Appender 장착은 매번 확인 | 내부 예외는 삼키고 Starter만 비활성 |
| ③ | AiopsLogbackAppender | ERROR + 예외 로그만 골라 다음 단계로 | `log.error()`를 부른 스레드 | `UnsynchronizedAppenderBase` 사용, 대기·네트워크 금지, 예외 던지기 금지, `dev.aiops` 로거 무시 | 그 로그만 건너뜀 |
| ④ | EventMapper | 예외 → `ErrorEvent` | ③과 같음 | 스택 최대 30줄, 원인 예외 체인 포함 | null 반환 → 건너뜀 |
| ⑤ | Masker | 민감정보 `***` 처리 | ③과 같음 | 이메일·토큰·`password=값`·따옴표 안 값·길이 제한, 단위 테스트로 고정 | 메시지를 비운 채 통과 (유출보다 누락) |
| ⑥ | EventBuffer | 스레드 사이 크기 제한 큐 | 넣기: 팀 앱 스레드 / 꺼내기: sender | 꽉 차면 `offer`가 false, 버린 개수 기록 | 일부 손실, 앱 영향 없음 |
| ⑦ | EventSender | 언제·얼마나 묶어 보낼지 판단 | aiops-sender 데몬 스레드 | 5초 또는 100개 중 먼저, 실패 시 1회 재시도 후 포기 | 그 묶음만 버림 |
| ⑧ | Transport | HTTP POST만 담당 | aiops-sender | Java 기본 `HttpClient`, 타임아웃 2~3초, 예외 대신 false | 최대 3초 대기 후 false |
| ⑨ | 시작 실패 처리 (AiopsRuntime.reportStartupFailure) | 시작 실패 원인 즉시 전송 | main | `ApplicationFailedEvent`의 예외를 직접 사용, 최대 3초 동기 전송 | 전송 실패 시 포기 |
| ⑩ | 종료 처리 (종료 훅) | 남은 큐 마지막 전송 | aiops-shutdown 훅 스레드 | 최대 2초. `kill -9`·강제 종료는 실행 안 됨 | 포기 |
| ⑪ | EnvCollector | 시작 시 `/v1/hello` 1회 | 준비 완료 후 sender가 전송 | 설정 **값은 절대 읽지 않음** | 포기 |

### 서버

| # | 부품 | 역할 | 실행 스레드 | 꼭 지킬 것 | 실패하면 |
|---|---|---|---|---|---|

| ⑭ | Fingerprinter / ErrorProcessor | 같은 원인 묶기 | `@Async` 처리 풀 | `process(tenantId, eventIds)` 형식 (D-081), 예외 타입 + 팀 코드 상위 3프레임(줄 번호 제외), `(tenant_id, fingerprint)` 유니크, 새 그룹만 다음 단계로 | processed=false로 남아 재처리 |
| ⑮ | PromptBuilder / LlmClient | 새 그룹 설명 1회 | 처리 풀, **트랜잭션 밖** | 지시와 에러 데이터 분리, 출력 "원인 후보 / 확인 방법 / 해결 방향", 일일 상한 | 설명 없이 알림, 나중에 재시도 |
| ⑯ | Notifier / DiscordWebhookNotifier | 새 그룹 알림 | 처리 풀 | 인터페이스로 분리, env별 채널, 분당 제한 | 로그만 남김 |
| ⑰ | RetentionScheduler | 원본 삭제 | 스케줄러 | `error_event`만 삭제 (local 3일, prod 14일) | 다음 날 재시도 |

## 4. 비기능 요구사항

| ID | 요구사항 |
|---|---|
| N1 | 서버가 죽어도 팀 앱은 정상 동작 |
| N2 | 팀 앱 요청 처리를 지연시키지 않음 |
| N3 | 키가 없으면 경고만 남기고 꺼짐 |
| N4 | 메모리를 무한히 쓰지 않음 (꽉 차면 버림) |
| N5 | 설정 값, 요청 본문, 헤더는 수집하지 않음 |
| N6 | 팀 프로젝트에 새 라이브러리를 최소로 추가 |

## 5. 결정 기록

| ID | 결정 | 이유 | 기각한 대안 |
|---|---|---|---|
| D-001 | 모노레포 + Gradle 멀티 모듈 | protocol을 Starter·서버가 같은 커밋에서 공유, 형식 불일치가 컴파일 단계에서 잡힘 | 멀티 레포 (형식 동기화 비용, 버전 맞추기 번거로움) |
| D-002 | protocol은 순수 Java record | 팀 앱에 무거운 의존을 끌고 들어가지 않기 | DTO에 Jackson 어노테이션 |
| D-003 | Starter의 Spring·Logback·Jackson은 `compileOnly` | 팀 프로젝트 버전을 강제하지 않음 (N6) | `implementation`으로 직접 포함 |
| D-004 | Spring Boot 버전은 1차 프로젝트와 동일하게 고정 (**4.1.1**, 2026-10-29 확인). Starter는 3.x 앱에서도 동작하도록 3.x·4.x 공통 API만 사용, 컴파일 타깃 Java 17 (D-084) | 첫 사용자가 1차 프로젝트 | 최신 버전 (팀 프로젝트와 불일치 위험) |
| D-005 | 초기 연결은 `spring.factories` 리스너, 순서는 로깅 초기화 직후 | Bean 생성 실패도 잡기 위해. 로깅 초기화 전에 붙이면 리셋되어 떨어짐 | `@AutoConfiguration` Bean |
| D-006 | 부품은 JVM당 1회 생성, Appender 장착은 이벤트마다 확인 | DevTools 재시작 시 로깅이 다시 초기화되어 Appender가 떨어짐 | 매번 새로 생성 (스레드·종료 훅 누적) |
| D-007 | Appender는 `UnsynchronizedAppenderBase` | `AppenderBase`는 모든 스레드가 한 줄로 서서 기다림 (N2 위반) | `AppenderBase` |
| D-008 | 버퍼 1,000개, 꽉 차면 버림 | N1, N4 | 대기(`put`), 무제한 큐 |
| D-009 | 전송 5초 또는 100개, 타임아웃 2~3초, 재시도 1회 | 배치로 비용 절감, 서버 장애 시 빨리 포기 | 이벤트마다 즉시 전송 |
| D-010 | `tenant_id`는 v0.1부터 모든 팀 데이터 테이블에 둠, RLS는 v0.2 | 나중에 격리를 붙이기 쉽게 | v0.2에서 컬럼 추가 |
| D-011 | DB 계정 3개를 v0.1부터 분리 | v0.2 RLS는 테이블 소유자에게 적용되지 않음 | 계정 1개 |
| D-012 | 커밋 메시지는 `타입(범위): 요약` | 변경 이력을 모듈 단위로 추적 | 자유 형식 |
| D-013 | `ErrorEvent.stack`은 바깥 예외의 프레임, 원인 예외는 `causes`(타입·메시지) | 팀 코드 프레임은 대개 바깥 예외에 있음. 단순화 | 원인 예외별 스택 전부 |
| D-014 | ~~4인 체제. 팀원 C는 모든 단계에서 통합 테스트·재현 시나리오를 소유~~ **(폐기 → D-067)** | — | — |
| D-067 | 4명 모두 개발. 단위 테스트는 부품 담당자가, 통합 테스트는 버전 책임자가 작성 | 테스트 전담자를 두면 그 사람의 개발 경험이 비고, 부품을 만든 사람이 자기 부품을 가장 잘 앎 | 테스트 전담 1명 (D-014) |
| D-079 | MVP(v0.1~v0.3)는 단계 담당제. `mvp-worklist.md` 18단계를 나/A/B/C가 나눠 갖고 그 단계의 작업 단위를 전부 개발 | 버전 셋이 한 덩어리(격리 없이 콘솔을 열 수 없음)라 버전 책임자가 의미 없음. 비슷한 기술끼리 묶여 학습 비용 최소 | 기능별 묶음, 버전별 1인 |

| D-068 | ~~v0.2부터~~ **v0.4부터** 버전 책임자 제도 (MVP는 D-079). 설계는 나, 핵심 로직·통합·머지·시연은 책임자, 나머지는 주변 부품으로 지원. 의존 없는 두 버전은 동시 진행 | 책임 소재와 포트폴리오 이야기가 분명함. 위험 버전(RLS·익명화)은 설계자가 직접 책임 | 버전 1명 전담 (앞뒤 의존 때문에 대기 발생) |

## 6. 분담

| 단계 | 나 | 팀원 A | 팀원 B | 팀원 C |
|---|---|---|---|---|
v0.1은 MVP(v0.1~v0.3)의 1부다. 단계 담당제(D-079)로 진행하며, 작업 단위와 확인 기준은 `mvp-worklist.md`에 있다. 4명 모두 개발하고, 자기 부품의 테스트는 각자 작성한다 (D-067).

| 단계 (worklist) | 부품 | 담당 |
|---|---|---|
| 환경·0·1 레포, protocol, DB·V1, 서버 뼈대 | ⓟ, 인프라 | 나 |
| 2 수집 API | ⑫ ⑬ | 팀원 A |
| 3 Starter 보내기 | ① ⑥ ⑦ ⑧ | 팀원 C |
| 4 Starter 잡기 | ② ③ ④ ⑤ | 팀원 C (마스킹 테스트는 나 선행) |
| 5 Starter 생명주기·안전성 5종 | ⑨ ⑩ ⑪, sample-app | 팀원 C |
| 6 그룹화·재처리 | ⑭ | 팀원 A (지문 테스트는 나 선행) |
| 7 LLM 설명 | ⑮ | 나 |
| 8 디스코드 알림 | ⑯ | 팀원 B |
| 9 보관 삭제·수집 통계 | ⑰ | 팀원 B |
| 10 배포·도그푸딩 | 인프라 | 나 |

**Starter 안전성 테스트 5종 (C 작성, 모두 통과해야 Starter 완료)**
1. 수집 서버가 꺼져 있어도 앱 정상, 응답 지연 없음
2. 키 없으면 경고만 남기고 꺼짐
3. 시작 실패 에러가 서버에 도착
4. 에러 1,000개 연속에도 메모리 그대로
5. 민감정보가 가려져서 도착

## 7. 팀원 AI 사용 고정 규칙

```
[AIOps v0.1 고정 규칙]
1. protocol 모듈의 클래스는 수정하지 않는다. 필요하면 담당자에게 먼저 요청한다.
```
